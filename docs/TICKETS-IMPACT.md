# Tickets v2 impact analysis

Prompt T0 — read-only analysis of the current application, the ticket v2 addendum, and existing business rules. This report plans later prompts only; it does not authorize or implement T1–T9.

## 1. Change map by addendum area

### A3 — Template, artwork, and printing

- **Current implementation:** `prisma/schema.prisma` models `EventBrandingAsset` and `PrintBatch`; `src/server/services/event-branding.service.ts` validates and converts poster/logo images; `src/lib/event-branding-storage.ts` manages files; `src/lib/pdf/ticket.tsx` renders the fixed green/gold ticket; `src/server/services/print.service.ts` loads tickets, decrypts tokens, renders, records print batches, and audits. Inventory/print screens are `src/app/(dashboard)/tickets/page.tsx`, `tickets/[id]/page.tsx`, `tickets/batches/[id]/page.tsx`, `src/components/tickets/ticket-preview.tsx`, `ticket-actions.tsx`, and `batch-print-actions.tsx`.
- **Planned additions/changes:** new `TicketTemplate` persistence and template config validation; artwork upload and authenticated retrieval; version/calibration state; configurable PDF rendering beside the current renderer; `PrintBatch` template/version/layout/output metadata; template list/editor/preview/activation screens. A8 routes add template list/create/patch/activate/preview/calibration and extend batch print output selection. `src/lib/permissions/index.ts` gains template-management and print capabilities as needed, checked in every service/route. Existing `src/app/api/v1/ticket-batches/[id]/print.pdf/route.ts` is the print endpoint to extend; `tickets/[id]/reprint` must preserve legacy batch/version behavior.

### A4–A5 — Scan-to-sell and buyer details

- **Current implementation:** `src/server/services/sales.service.ts` creates quantity-based sales, selects oldest `AVAILABLE` tickets, marks them `SOLD`, inserts `SaleTicket`, optional initial payment, and audit entries in a transaction. `SaleTicket.ticketId` is unique. `src/lib/validation/sales.ts`, `src/app/api/v1/sales/route.ts`, `src/components/sales/sale-create-form.tsx`, `src/app/(dashboard)/sales/new/page.tsx`, and sales list/detail pages form the sales flow. The camera scanner is `src/components/check-in/scanner.tsx`; admission uses `/check-in/verify-qr`, `/verify-serial`, and `/confirm` through `check-in.service.ts`.
- **Planned additions/changes:** read-only sale lookup by token or permitted serial, scan-to-sell cart and buyer/payment collection, exact-ticket sale allocation, entry method and scan timestamp, manual-sale policy/permission, normalized phone and buyer notice, sale audit and lookup attempts. Add `ScanAttempt.purpose` while preserving admission as its old/default purpose. Keep lookup entirely separate from admission; it must not call confirm or alter inventory. Existing sales endpoint becomes a discriminated scan/manual/bulk boundary and retains the quantity path for admin only. Event settings and detail DTOs need the new policies. New/changed paths include `sales.service.ts`, `check-in.service.ts` only for shared scan-attempt representation if needed, sales validation/routes/components/pages, and `src/lib/permissions/index.ts`.

### A6 — Seller stock and remittances

- **Current implementation:** no custody, stock issue, seller statement, close-out, or remittance models/services/pages/routes exist. `Sale.sellerId` is the authenticated actor; sale/payment history is append-only where financial corrections are concerned.
- **Planned additions:** `TicketCustody`, `StockIssue`, `Remittance` and linked reversal relation; issue/return/loss/close-out and remittance services; issue slip and seller statement PDFs; stock, return/close-out and remittance screens; reports/audit additions. New API routes are the A8 `/stock/*` and `/remittances*` endpoints. The existing `Ticket.status` continues to represent inventory only: custody must not be folded into it.

### A7 — Schema and migrations

- **Tables/columns:** add `TicketTemplate`; extend `PrintBatch`; add event policy/notice fields; add normalized phone on `Sale`; extend `SaleTicket` with entry method/time; extend `ScanAttempt` with purpose; add `TicketCustody`, `StockIssue`, and `Remittance`.
- **Integrity:** preserve current unique serial/token hash, unique `SaleTicket.ticketId`, unique check-in, event/type foreign keys, integer UGX and current append-only payments/check-ins. Add positive/non-negative amount and quantity checks, appropriate FKs/indexes, and a partial unique index on custody `ticketId` where `releasedAt IS NULL`. Verify range checks and query indexes as each schema design is made in its own prompt.
- **Partial unique index in Prisma 7.10.1:** it can be represented in `schema.prisma` using the `partialIndexes` preview feature and `@@unique([ticketId], where: { releasedAt: null })` (or the documented raw predicate form). Prisma ORM 7.4 added partial-index create/introspection support; the pinned project version is 7.10.1. A hand-written SQL migration is therefore not inherently required for this index, though the generated migration must be inspected and tested. Source: [Prisma ORM v7 index docs](https://docs.prisma.io/docs/orm/v7/prisma-schema/data-model/indexes) and [Prisma 7.4 partial-index release note](https://www.prisma.io/changelog/2026-02-11).
- **Existing migration style:** this repository uses standard Prisma Migrate timestamped directories containing `migration.sql`. Those migrations already include hand-authored PostgreSQL `CHECK` constraints, indexes, and FK adjustments in SQL. New schema migrations can similarly use generated SQL reviewed and supplemented in `migration.sql`; use a new migration for a change that has already been deployed, never rewrite applied history. The project runs `prisma migrate deploy` in the Docker startup command. Prisma's official [customizing migrations guide](https://www.prisma.io/docs/orm/migrations/workflows/customizing-migrations) documents creating a draft with `migrate dev --create-only`, editing its SQL, then applying it.
- **Compatibility/backfill:** keep added policy columns nullable only during a deliberate migration/backfill if needed, then finalize safe defaults. Existing `Sale` name/phone remain nullable in storage; policy-required collection is enforced at service boundary so old records remain readable. Backfill legacy `SaleTicket` rows to `BULK` with no scanned timestamp and legacy `ScanAttempt` rows to `ADMISSION`. Existing print batches get null template/version/layout fields and retain the legacy print path; existing token hashes and encrypted tokens are not rewritten. New templates start DRAFT with PLACEHOLDER zones. Do not fabricate custody for historic tickets/sales: legacy tickets begin unissued; sellers subject to `requireStockIssue` must receive an explicit stock issue before selling them. Sold historical tickets stay sold and do not receive active custody. Remittances begin with no fabricated opening balance. Keep all historical Sales and payments intact.

### A8–A9 — API and authorization

- **Existing related endpoints:** `src/app/api/v1/sales/route.ts`, `sales/[id]/*`, `ticket-batches/[id]/print.pdf/route.ts`, `tickets/[id]/reprint/route.ts`, `events/[id]/branding/route.ts`, `branding/[storageKey]/route.ts`, and check-in verification/confirm and scan-attempt routes.
- **New endpoints:** A8 template CRUD/activation/preview/calibration, sale lookup, stock issue/return/loss/statement/slip, and remittance create/reverse. Extend sales create and ticket-batch print endpoints. Validate every request with Zod, require idempotency on mutations, use stable error codes, limit lookup and sale traffic, and enforce event access on the server. Reuse deny-by-default role checks; do not grant supervisor options by implication. In particular, A9's seller-only/optional supervisor cases need explicit permission mapping and tests.

### A11–A13 — Screens, reports, audit, and privacy

- **Current screens to extend:** sales create/list/detail; ticket inventory/batch printing; event detail/settings and event branding manager; dashboard/report/audit pages. Current `src/app/(dashboard)/scanner/page.tsx` and `CheckInScanner` are admission-specific and should remain so. New screens: Sell, My Stock, Ticket Templates, Issue Stock, Returns/Close-out, Remittances, and restricted gate buyer-detail reveal.
- **Reports/audit additions:** seller reconciliation, stock by holder/status, issue slips, remittances, entry method, and template/calibration history. Reuse audit service/schema and report CSV/PDF patterns. Never put raw tokens in lookup logs, attempt records, query strings, audit, exports, or normal DTOs. Buyer contact stays hidden from verifier surfaces; each privileged gate reveal needs an audit event. Template artwork may use public-style serving only if deliberately approved; addendum requests authenticated retrieval and prohibits public upload exposure.

### A14–A16 — Verification and launch dependencies

- Add integration coverage for ticket-by-token sale and wrong-ticket prevention, all lookup states/read-only behavior, one-sale concurrency across sellers, one-active-holder issue concurrency, policy and permission denial, normalized Uganda phone formats, append-only remittance/reversal, buyer privacy, template validation/version/calibration, and continued admission/payment tests.
- Production acceptance additionally depends on measured template zones, calibration and production paper scans on two Android phones, real-phone seller concurrency, and stock handover/close-out walkthrough. These cannot be established by unit tests alone.
- Open decisions in A16 remain owner inputs: measured zones/perforation, exact fields and price display, layout/printer, embedded artwork fonts, buyer notice, manual seller sales, supervisor stock/remittance privileges, replacement serial process, and data retention. Keep them configurable or PLACEHOLDER; production activation must remain blocked until measured zones and calibration are recorded.

## 2. Migration plan and data safety

1. Additive migration: nullable template/print metadata, event policies with explicit safe defaults, nullable normalized phone, legacy-safe `SaleTicket.entryMethod = BULK`, `SaleTicket.scannedAt = NULL`, and `ScanAttempt.purpose = ADMISSION`. If the generated migration cannot preserve/backfill defaults safely, split add/backfill/constraint steps.
2. Add template and stock tables with restrictive FKs where historical records must remain; indexes for event, seller, ticket, and timestamps. Store template artwork path/checksum/pixel dimensions, immutable version, and status separately from event poster/logo.
3. Add custody uniqueness for active holder. In Prisma schema use the Prisma 7.10.1 preview partial unique feature; review generated PostgreSQL predicate SQL. Migration should fail visibly if any pre-existing custody rows violate the predicate; no legacy custody rows exist before this feature, so there is no historical holder backfill.
4. Add remittance amount `CHECK > 0` and reversal self-reference, preserving original remittances. Corrections insert linked reversals; no update/delete workflow.
5. Keep old print rows nullable and reprint through legacy generator when template metadata is absent. New production batch stores template id/version, sheet layout snapshot, output kind. A used template version is never edited in place.
6. Validate upgrades from both clean schema and current production-like schema; confirm all existing tickets, sales, payments, token ciphertext, print batch references, and check-ins survive unchanged.

## 3. Branding reuse

`src/server/services/event-branding.service.ts` provides useful patterns: admin checks, signature sniffing, Sharp decoding/limits, random opaque keys, storage writes outside `public`, DB transaction plus audit, and safe cleanup. `src/lib/event-branding-storage.ts` provides path-safe file operations and `BRANDING_STORAGE_DIR`; Compose mounts this at `/var/lib/ksp-gatepass/branding`. The existing event branding API serves poster/logo variants from a route, currently public-facing.

Template artwork must have separate validation/metadata because it allows PNG/JPEG only, 40 MB (not current 5 MB), 40 MP, RGB, aspect tolerance 1%, and exact ticket-plus-bleed expected dimensions. Preserve original-resolution bytes for print, strip metadata while retaining required color profile, and do not reuse the 480/1200px WebP derivatives as print artwork. Reuse safe key/path and storage volume mechanics, not the current public-display response or replacement semantics: template versions must retain old assets while production print batches refer to them. Add authenticated artwork read route and audit upload/replace/activate/retire without file bytes.

## 4. PDF renderer capability probe (actual render, no dependency changes)

A throwaway CommonJS script and outputs were created under `%TEMP%/ksp-tickets-v2-renderer-probe`, outside the repository. It used the already installed `@react-pdf/renderer` 4.9.0, React, and Sharp; no package install or repo file was changed. It generated a 2551 × 768 PNG, rendered documents with 5 and 100 ticket instances, and inspected the resulting PDF objects/content streams.

| Capability | Result | Evidence/limit |
| --- | --- | --- |
| Full-resolution PNG artwork | Pass | PDF image XObject reports `/Width 2551 /Height 768`, matching source pixels. |
| Custom TTF embedded | Pass | Registered `C:\Windows\Fonts\arial.ttf`; output contains subset Arial font (`CZZZZZ+ArialMT`) and `/FontFile2`. Runtime font path remains a deployment concern below. |
| Vector QR using `Svg` | Pass | Test QR modules were `Rect` shapes under `Svg`; PDF content has vector paint/path operations, not an image XObject for the QR. The production renderer must draw the actual token's QR matrix in vector form. |
| 90° and 270° text transforms | Pass | Decompressed PDF page stream contains both rotation matrices `0 1 -1 0 … cm` and `0 -1 1 0 … cm`. This confirms renderer transform support; final zone placement/clipping still needs visual and physical validation. |
| Crop marks | Pass | SVG line strokes appear in the PDF content stream. |
| Exact page size | Pass | A4 page MediaBox is `0 0 595.275574 841.889771 pt`, corresponding to 210 × 297 mm. |
| Repeated artwork on 5 tickets | Duplicated | 5 source instances produced 5 image XObjects; PDF size 154,452 bytes. |
| Repeated artwork on 100 tickets | Duplicated | 100 source instances produced 100 image XObjects; PDF size 2,863,665 bytes (about 18.5× the 5-ticket file). The test artwork is a simple flat-color image and compresses unusually well; actual artwork may be much larger. At 500 tickets, per-ticket embedding is a material output-size risk. |

The current `src/lib/pdf/ticket.tsx` rasterizes each QR to PNG using `qrcode` and constructs an image for each ticket; it does not meet the addendum's vector QR requirement. The test shows `@react-pdf/renderer` has the primitives needed, but artwork must be deduplicated/cached as a single PDF image resource per document. Measure 500-ticket output and memory before accepting a production renderer design. No renderer dependency is proposed by this analysis.

## 5. Scanner reuse and token flow

`src/components/check-in/scanner.tsx` already implements Android browser camera capture with `@zxing/browser`, torch handling, server-connectivity gating, camera failure states, and serial entry. Its current callbacks are tied to gate admission endpoints, admission result UI, and gate/session state. Reuse the camera lifecycle/decoder patterns in a dedicated sale scanner/cart, not its admission confirmation function or green admitted result. Sale scan submits the decoded token to a read-only lookup; successful lookup adds the exact item to the cart; final confirm sends scanned token(s) to a sale service which hashes tokens, locks/rechecks eligibility for sale, and creates Sale/SaleTicket/payment/audit atomically. Unknown/offline/error, duplicate cart item, seller mismatch, and race-lost responses must never appear as successful sales.

Today `src/server/services/print.service.ts` is the only service that calls `decryptToken(ticket.tokenEnc)`. `src/lib/qr/token-vault.ts` decrypts AES-256-GCM ciphertext using `TOKEN_ENCRYPTION_KEY`; `src/lib/config.ts` requires a 32-byte base64url key. `tokenHash` remains the lookup value and `tokenEnc` is only used to recreate the identical QR for printing. In the future, both sheet and data-only layer outputs can use this existing authorized print path: decrypt only while preparing PDF rows, pass token to the renderer in memory, and persist/audit only safe batch metadata. Do not store token plaintext in new template/batch records or log it, expose it in URLs, or return it through APIs/exports.

## 6. Risks, conflicts, and runtime packaging

- **Sales model conflict:** existing quantity sale allocates server-selected oldest tickets; addendum replaces this for pre-printed stock, while retaining an admin-only bulk path. Preserve existing records and make entry method explicit.
- **Custody vs inventory:** custody is a separate fact and needs database uniqueness plus transactional issue/sale/return/loss coordination. Sale and custody updates must commit together to avoid sold tickets remaining held.
- **Admission remains unchanged:** old admission policy and transactional check-in must remain authoritative; seller lookup cannot use check-in endpoints. A4's full-payment language and PRD event payment policy must be reconciled consistently in sale eligibility and admission.
- **Buyer data privacy:** current seller sale DTO includes buyer fields for own sales. Gate result DTOs must not inherit that shape. A gated audited reveal must be narrow and separately authorized.
- **Partial unique-index feature:** in Prisma 7.10.1 this is schema-expressible behind preview flag, but it must be enabled and migration output reviewed; do not silently assume stable GA behavior.
- **PDF size:** renderer probe proves repeated image nodes duplicate artwork resources. A shared embedded XObject or another compliant method is required; otherwise 500 copies of a high-resolution image can create very large PDFs and memory load.
- **Docker runtime:** `Dockerfile` sets `WORKDIR /app`; production Compose mounts the upload volume at `/var/lib/ksp-gatepass/branding` and sets `BRANDING_STORAGE_DIR` there. `event-branding-storage.ts` falls back to `path.join(process.cwd(), '.data/event-branding')` only when unset, and resolves all paths from working directory. In the runner image, source files and `.data` are not copied as branding assets, but the named volume is mounted and writable; this is intentional for uploaded images. Next output file tracing is not explicitly configured (no standalone output setting); dynamic assets in the external volume must be read at runtime from DB-derived safe keys and must not be expected in the Next bundle. Fonts are the gap: no project font files are currently present, and a Windows/system absolute font path would work in dev but fail in the Linux `node:24-alpine` image. Production font files should be checked into the app (or otherwise explicitly copied into the runner stage), referenced relative to `/app` or resolved from a stable module path, then verified in the built image. Do not store generated/user fonts in a developer-only directory. `Dockerfile` currently copies `.next`, `public`, scripts, and selected source helpers; any future static font must either be in `public` and copied by `COPY public ./public` or explicitly copied to the runner. Runtime-loaded fonts may also need explicit file-tracing/copy treatment depending on how `Font.register` resolves its path; verify from the actual container. `next.config.ts` currently has no `outputFileTracingIncludes` or standalone configuration. The external volume path is not a bundled file and should not be added to tracing. |
- **Conflicting details:** A3.4 says no buyer data is printed, while PRD 5.6 lists buyer details as optional; addendum wins for printing. Existing check-in policy remains unchanged. Rule 16 limits sale entry methods; quantity sales remain only an admin bulk path. Rule 25's narrowly audited supervisor/admin gate reveal must not weaken the existing verifier privacy rule.
- **Operational dependencies:** actual zone coordinates, intended artwork and fonts, printer layout, buyer notice, supervisor overrides, data retention, and real paper scans remain unresolved as called out in A16.

## 7. Recommended build order and task list (T1–T9)

1. **T1 — Template model, upload, zones:** schema/migration and partial unique prerequisites; Zod config with trim bounds and QR minimums; original artwork upload/storage/authenticated read; immutable template versions; placeholder development template; admin-only APIs, audit, idempotency, validation/upload/permissions tests.
2. **T2 — Renderer and print outputs:** deduplicated artwork embedding; embedded project TTFs; vector QR; sheet/single/data-layer/calibration PDFs; exact layouts and crop marks; template version/layout snapshot on PrintBatch; legacy fallback; measure output size for 500 tickets and test reprints/token stability.
3. **T3 — Template admin UI:** mobile-first upload, version/status/calibration screens, measured zone editor/preview/import, and activation blockers; follow `docs/DESIGN.md`.
4. **T4 — Scan-to-sell backend:** policy and buyer phone fields, lookup purpose/state, rate limiting, token-hash lookup, exact-ticket atomic sale/payment/audit, manual and admin bulk modes, seller custody check, idempotency, race and read-only tests.
5. **T5 — Scan-to-sell UI:** separate seller scan/cart flow, phone normalization feedback, duplicate prevention, online/error states, payment confirmation and receipt.
6. **T6 — Seller stock backend:** custody, issue groups, active-holder partial unique constraint, atomic issue/return/loss/revoke/close-out; signed slip data; append-only remittance/reversals; permissions and concurrency tests.
7. **T7 — Stock and seller UI/reports:** My Stock, issue/return/loss/close-out and remittance screens, issue slip PDF, seller statement, stock/reconciliation reports.
8. **T8 — Permission, audit, privacy sweep:** role/event scoping for all new APIs, buyer detail boundary/reveal auditing, token/log/export review, audit coverage and adversarial permissions tests.
9. **T9 — Real-world tests and release gate:** real PostgreSQL migration/concurrency suite, existing check-in/payment regression, paper print and QR scans on two Android phones, two-seller race, stock lifecycle walkthrough, and update release gate checklist.
